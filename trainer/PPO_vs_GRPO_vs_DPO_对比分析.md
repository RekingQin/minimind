# PPO vs GRPO vs DPO 训练效率对比分析

> 基于 MiniMind 项目（hidden_size=768, num_hidden_layers=8），batch_size=32

---

## 1. 算法定位对比

| 维度 | DPO | GRPO | PPO |
|------|-----|------|-----|
| 全称 | Direct Preference Optimization | Group Relative Policy Optimization | Proximal Policy Optimization |
| 是否在线生成 | ❌ 离线数据 | ✅ 在线生成 | ✅ 在线生成 |
| 是否需要 Reward Model | ❌ | ✅ | ✅ |
| 是否需要 Critic | ❌ | ❌ | ✅ |
| Advantage 来源 | 无（直接用偏好对） | 组内相对排序 | GAE 时序差分 |
| 训练稳定性 | ⭐⭐⭐ 最稳定 | ⭐⭐ 中等 | ⭐ 需调参 |
| 训练效率 | ⭐⭐⭐ 最快 | ⭐⭐ 中等 | ⭐ 最慢 |

## 5. 为什么 GRPO 反而比 PPO 慢？

直觉上 GRPO 没有 Critic 应该更快，但实际上：

```
┌─────────────────────────────────────────────────────────────────┐
│ GRPO 的隐藏开销：num_generations=6                               │
│                                                                  │
│ 每个 prompt 生成 6 条回复:                                        │
│   batch_size=32 → 实际生成 32×6 = 192 条序列                     │
│                                                                  │
│ vs PPO 每个 prompt 只生成 1 条:                                   │
│   batch_size=32 → 实际生成 32×1 = 32 条序列                      │
│                                                                  │
│ GRPO generate 量 = PPO 的 6 倍!                                  │
│ GRPO RM 打分量 = PPO 的 6 倍!                                    │
└─────────────────────────────────────────────────────────────────┘
```

所以：**GRPO 的总生成量（192条）远超 PPO（32条）**，虽然 GRPO 省了 Critic 和多轮更新，但被 6 倍的生成量吃回去了。

## 7. GRPO 的 num_generations 已经是批量并行的

### 常见误解

> "GRPO 每个 prompt 生成 6 次，能不能把 6 次展开成大 batch 一次性推理？"

**实际上代码已经这样做了！** 看 `rollout_engine.py` 中的实现：

```python
# batch_size=32, num_generations=6
# → repeat_interleave 展开 → 实际传给 generate() 的 batch = 32×6 = 192 条
output_ids = model.generate(
    input_ids=prompt_ids.repeat_interleave(num_generations, dim=0),  # [192, P]
    ...
)
```

并**不是**对每个 prompt 串行调用 6 次 `generate()`，而是把 32×6=192 条序列打包成一个大 batch，**一次 `generate()` 调用同时并行生成 192 条**。

### 那为什么还是慢？

因为 `generate()` 的瓶颈不在 batch 维度，而在**序列长度维度（自回归的时间步）**：

```
generate() 内部循环:

for step in range(max_new_tokens):          # 1024 步，每步必须等上一步完成
    logits = model(input_ids)               # batch=192 在 GPU 上并行 ✅
    next_token = sample(logits[:, -1, :])   # 采样下一个 token
    input_ids = cat(input_ids, next_token)  # 拼接，进入下一步

═══════════════════════════════════════════════════════════════
  可并行维度              不可并行维度
═══════════════════════════════════════════════════════════════
  batch (192条)  ✅      时间步 (1024步)  ❌ 串行依赖
  GPU 已充分利用          第 t+1 步必须等第 t 步输出
═══════════════════════════════════════════════════════════════
```

### 增大 batch 是否能继续加速？

```
┌─────────────────────────────────────────────────────────────────┐
│  generate() 耗时 vs batch_size 的关系（固定 max_new_tokens）：    │
│                                                                  │
│  时间                                                            │
│  ▲                                                               │
│  │         ╭──────────────────── 显存不足 OOM                    │
│  │        ╱                                                      │
│  │  ─────╱─────────────────────── 计算瓶颈（线性增长）            │
│  │ ╱                                                             │
│  │╱  ← GPU 未跑满区间（增大 batch 几乎不增加时间）               │
│  └────────────────────────────────────────→ batch_size            │
│     32    64   128   192   256   384                             │
│                 ↑                                                 │
│           GPU 利用率拐点                                          │
└─────────────────────────────────────────────────────────────────┘
```

- **batch < 拐点**：GPU 算力未填满，增大 batch 几乎不增加时间（"免费并行"）
- **batch > 拐点**：GPU 已满载，时间线性增长；且 KV Cache 显存也线性增长，可能 OOM

对于 MiniMind-768 这种小模型，192 条的 batch 大概率已经超过 GPU 利用率拐点，
所以降低 num_generations (6→4) 确实能减少约 33% 的生成时间。

### 真正的加速方向

自回归生成的**序列串行性**是 Transformer decoder 的本质限制，要加速只能：

| 方向 | 原理 | 效果 |
|------|------|------|
| **缩短序列** | 降低 max_gen_len 1024→512 | 直接减半时间 |
| **投机解码** (Speculative Decoding) | 小模型猜多个token，大模型一次验证 | 2-3x 加速 |
| **SGLang/vLLM** | PagedAttention + RadixAttention + Continuous Batching | 1.5-3x 加速 |
| **量化推理** | INT8/INT4 减少每步计算量 | 1.5-2x 加速 |
| **减少生成数** | num_generations 6→4 | 在 GPU 满载时线性减少 |

## 8. 优化建议汇总

| 优化方向 | 方法 | 适用于 | 预期加速 |
|---------|------|--------|---------|
| 加速生成 | 使用 SGLang/vLLM 推理引擎 | GRPO, PPO | 1.5-3x |
| 减少生成步数 | 降低 max_gen_len (1024→512) | GRPO, PPO | ~2x |
| 减少生成量 | 降低 num_generations (6→4) | GRPO | ~1.3x |
| 投机解码 | Speculative Decoding | GRPO, PPO | 2-3x |
| RM 批量化 | 将 RM 改为 batch 推理 | GRPO, PPO | RM 部分 5-10x |
| 避免在线生成 | 改用 DPO/SimPO 等离线方法 | - | 30-50x |
| 异步 Rollout | 生成和训练流水线化（Actor-Learner 分离） | GRPO, PPO | ~1.5x |
| 量化推理 | generate 阶段用 INT8 | GRPO, PPO | ~1.5x |

## 9. 总结选择建议

```
速度优先？     ──→  DPO（快 30-50x，但需要离线偏好数据）

效果优先？     ──→  GRPO/PPO（在线学习，能探索更优策略）

显存紧张？     ──→  DPO > GRPO > PPO（模型数量递增）

工程复杂度低？ ──→  DPO > GRPO > PPO（DPO 最简单）

适合 Agent？   ──→  GRPO/PPO（Agent 需要在线交互探索）
```
